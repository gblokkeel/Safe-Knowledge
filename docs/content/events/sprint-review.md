# Sprint Review (Iteration Review)

## Overview

The **Sprint Review** (called **Iteration Review** in SAFe) is the team-level ceremony at the end of each sprint where the team demonstrates completed work to the Product Owner and stakeholders, and receives feedback. It is the team's primary feedback loop for business value alignment.

## Purpose

1. **Demonstrate completed work** — Show working software, not slides
2. **Receive feedback** — PO and stakeholders provide input on what was built
3. **Accept completed stories** — PO formally accepts stories that meet acceptance criteria
4. **Adjust the backlog** — Incorporate feedback into the Team Backlog
5. **Celebrate progress** — Acknowledge the team's work

## Participants

| Role | Attendance |
|------|------------|
| **All Team Members** | Required — demonstrate their work |
| **Product Owner** | Required — accepts work; provides feedback |
| **Scrum Master** | Required — facilitates |
| **Stakeholders** | Invited — provide feedback |
| **Product Manager** | Occasional — especially for significant features |
| **Business Owners** | Occasional — for major business capability delivery |

## Duration

- **1-week sprint**: ~1 hour
- **2-week sprint**: ~1–2 hours
- **PI System Demo** replaces the end-of-PI Sprint Review (all teams demo together)

## Structure

### 1. Sprint Opening (5–10 min)
- SM or PO reviews the Sprint Goal and selected stories
- Brief context: "Here's what we set out to accomplish"

### 2. Story Demonstrations (30–60 min)
- For each completed story:
  - Team member demonstrates the working feature
  - Demonstrates in a working environment (not mockups)
  - PO and stakeholders ask questions

### 3. Feedback and Discussion (15–20 min)
- PO and stakeholders provide feedback
- Questions: "Does this meet the need?" "What would make this better?"
- Notes captured for backlog items

### 4. Story Acceptance (10–15 min)
- PO accepts or rejects each completed story
- Acceptance = meets all acceptance criteria + meets Definition of Done
- Rejected stories are returned to the backlog (or re-planned)

### 5. Sprint Review Retrospective (optional, separate event)
- Sometimes combined with Sprint Retrospective; better kept separate

## Story Acceptance vs. Done

A story is "Accepted" by the PO when:
- All acceptance criteria are met
- The Definition of Done is satisfied
- The PO has seen and validated the working feature
- No critical defects remain

Stories should not be accepted based on code completion alone — the PO must see the feature working.

## Feedback Loop

The Sprint Review creates a continuous feedback loop:

```
Build → Demo → Feedback → Update Backlog → Build...
```

This feedback loop is essential for:
- Course-correcting before building more of the wrong thing
- Incorporating new insights from seeing working software
- Building stakeholder engagement and trust
- Validating that requirements were understood correctly

## Sprint Review vs. System Demo

| Aspect | Sprint Review | System Demo |
|--------|--------------|-------------|
| **Scope** | Single team's work | Entire ART's integrated work |
| **Frequency** | Every sprint | Every PI (+ optional mid-PI) |
| **Audience** | Team + team stakeholders | ART + Business Owners + customers |
| **Integration** | Team-level integration | Full ART integration |
| **Feedback** | Immediate story-level feedback | PI-level business feedback |

## Common Anti-Patterns

| Anti-Pattern | Impact |
|-------------|--------|
| **No PO attendance** | Stories accepted without business validation |
| **Sprint Review is a slideshow** | Violates the principle of working software |
| **Demo in dev environment with test data** | Stakeholders can't evaluate real user experience |
| **Treating acceptance as rubber stamp** | Quality and fit-for-purpose isn't validated |
| **No stakeholders beyond PO** | Missed feedback opportunity |
| **No backlog updates from feedback** | Feedback is collected but not acted on |
